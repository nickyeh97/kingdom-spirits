## 目的與適用範圍

讓使用者接手後能直接修改、貼圖、綁定或輸出，逐步接近其遊戲／影視工作流程的要求。渲染好看是品質的一部分，不能代替造型、拓撲、UV、效能與交接驗證。

這是經資產實測形成的 blendsmith 專案約定，不宣稱是全產業通用標準或品質認證。使用者明確指示優先；同意的差異須記入製作簡報。遊戲與影視使用不同預算與輸出條件，必須按每個資產確認。每次建置都記錄實際使用的 Blender 版本。若專案設定檔列出多個版本（例如使用者桌機版與助手無頭模式版），生成腳本必須在所有版本都能執行；使用特定版本的 API 前先確認相容性。

**專案設定檔：**開始任何工作前，若 repo 有美術設定檔就先讀（本 repo 為 `art/ART_PROFILE.md`）。其中的決定——風格模式、目標引擎、預算、配色遮罩慣例、交付位置、worklog 位置——都視為使用者已明確確認的指示，直接沿用、不重複詢問；使用者變更專案層級的決定時，同步更新設定檔。

若本次只要求規範整理或檢查，只做該範圍。局部修正任務發現其他缺陷時，記錄影響並提出建議，不擅自擴充成整個資產重建。

## 使用者需求模板

適用時提供[英文正本](assets/user-request.template_EN.md)或[繁體中文閱讀與填寫副本](assets/user-request.template.zh-TW.md)。自由文字需求也要套用基本資料檢查。即使使用者用自由文字描述、沒有填表，也要主動詢問基本模板中尚未提供且適用的項目。提問、解釋選項與需求總結，配合使用者正在使用的語言或明確指定的語言；技術通道名稱可保留英文。儲存的 skill、brief 與 worklog 仍以英文為正本。沿用已提供或已確認的答案；空白代表缺少資訊，不代表「不需要」或允許自行猜測。使用者不知道時，提出具體選項與取捨，把建議納入確認摘要；明確授權判斷可以結案，沉默不可以。相關缺項分組詢問，保留未答項目，等待時可繼續分析參考。先確認 Rig 是否不需要／保留／新增；不需要 Rig 時，其細節不適用。同樣，不交付渲染圖時，打光與圖片設定可記為不適用。不強迫填無關的進階欄位，也不重問已有答案的項目。

將資料整理為既有製作 brief 與 R04 完整摘要，不增加另一道批准，也不取代已確認範圍。除非專案設定檔已決定，先問風格模式（R02：NPR 卡通或 PBR）與目標引擎。明確詢問圖集數量、解析度與 UDIM。PBR 模式預設 BaseColor、Normal、Roughness、Metallic，補問額外通道；NPR 模式則詢問配色方式（頂點色遮罩或調色盤貼圖）、描邊方法與可選的遮罩。拓樸選項含全四邊形、全三角形、混合與其他；「其他」的具體表示方式及與 R03 的個別資產差異，納入摘要釐清，使用者明確指示優先。酒瓶數字不是通用預設。

## 使用者明確要求：R01–R04

### R01 — Shader Editor 可讀、可改

所有交付材質及其內部群組的節點都要梳理。由左至右安排「座標／貼圖 → 調整 → BSDF → Output」，以 Frame 區分用途，給貼圖、群組和主要參數有意義的名稱。節點與標籤不得互相遮住，接線可追蹤；不要用大量折疊或黑箱群組掩蓋混亂。用實際 Shader Editor 畫面確認，不只看程式碼設定了座標。

每個材質最左側使用 Ctrl+T 形式的 **Texture Coordinate → Mapping → Image Texture** 配置。依 UV 製作的貼圖使用 UV 座標，Mapping 輸出必須接到每張圖片，包括 Normal、Roughness、Metallic 與額外遮罩。可以用程式建立等效節點，不要求交付環境安裝 Node Wrangler。同一貼圖組的對齊通道共用 Mapping，初始變換保持不偏移、不旋轉、縮放為 1，以保留已確認外觀。只有表面需求不同時才分開座標鏈，並標示用途；調整後檢查通道對齊與切線法線效果。

### R02 — 開案時決定風格模式：NPR 卡通或 PBR

專案第一次做 R04 完整摘要時（或該資產所屬專案尚無設定檔時），決定並記錄一種**風格模式**。同一個資產內不得混用，也不得默默切換；之後要換模式，視為新的範圍。

- **NPR／卡通模式**（卡通、低多邊形）：Toon 思維加上描邊（Outline）。見下方〈NPR／卡通模式要求〉。
- **PBR 模式**（以物理為基礎，寫實或風格化寫實）：完整 BSDF 思維，加上 BaseColor、Normal、Roughness、Metallic 四張貼圖。見下方〈PBR 模式要求〉。

R01（可讀的 Shader）、R03（拓撲與每個網格都要 UV）、R09（貼圖資料夾）兩種模式都適用。

#### NPR／卡通模式要求

讓形狀與平塗色塊承擔辨識度，而不是表面微細節。

- **輪廓優先：**在最小的預定螢幕尺寸下，只看剪影也要認得出來。三角形花在輪廓上，不花在鏡頭看不清的小零件。
- **卡通著色（Toon shading）：**明暗是由色階（ramp）產生的少數幾段硬邊光帶（通常兩到三段），不是 PBR 的連續漸層。光帶由引擎 shader 產生；不要把光影或投影畫進顏色資料。
- **一定要有描邊（Outline）。**依目標引擎選定並記錄方法：反向外殼（inverted hull，多一層稍微膨脹、只畫背面的外殼）、沿法線外推的 shader pass，或螢幕空間的後處理邊緣偵測。外殼或外推描邊要檢查硬邊處的連續性：分離的法線會讓描邊斷開；接收端 shader 支援時，提供平滑（平均）過的描邊用法線——例如存在頂點色或備用 UV 通道——並記錄做法。
- **顏色交付：**使用「配色遮罩頂點屬性＋材質參數」（換配色不用新貼圖），或在 UV 上使用小張的調色盤／圖集貼圖。NPR 模式不要求 Normal、Roughness、Metallic 貼圖，除非使用者要求；可選的貼圖（花紋遮罩、發光遮罩）依 R09 管理。
- **Blender 預覽要接近引擎效果：**準備一個可讀（R01）的預覽材質，套用與引擎 shader 相同的配色公式；可行時加上卡通色階（EEVEE 的 *Shader to RGB* → *Color Ramp* 設 Constant）與反向外殼描邊預覽。最終效果以引擎 shader 為準，不是 Blender 預覽；差異要記錄。
- **平滑或平面著色**是每個零件的美術決定（柔軟形體通常用平滑，俐落切面用平面），要記錄。下方的烘焙規則只在 NPR 也要烘焙貼圖時適用。

#### PBR 模式要求

最終資產使用的每個表面材質組至少具備實際可交付、可重新編輯並正確連接的 **BaseColor、Normal、Roughness、Metallic／Metalness** 四種貼圖。可以共用材質組、圖集與貼圖，不要求每個物件重複產生相同影像；每個使用中的材質必須可追溯到其貼圖組。

程序材質可用於製作與調整，但不能把四個數值插槽或四個空白檔案當成已完成四張貼圖。程序效果需烘焙／輸出到確認的 UV。材質本來均勻的通道可使用有物理依據的常數貼圖，例如非金屬的 Metallic=0；須記錄用途，不為湊數捏造細節。

依材質判斷是否需要 emission mask、alpha、displacement、透射、次表面、塗層等；不是有四張圖就已充分還原材質。Alpha 通道可以承載發光區域遮罩，但遮罩要用來控制發光，**不因此自動連到表面透明度**。色彩空間、法線接法、UDIM 與打包驗證見 [production-checklist.md](references/production-checklist.md)。

生成貼圖前先理解參考中的材質、塗層、表面處理及細節尺度，用 BaseColor、Roughness 與 Normal 表現該材質特徵，不套用通用噪點充數。紙張需考慮纖維、孔隙、塗層和印刷，並在預定觀看距離、中性光與掠射光下判斷強度。使用者要求時強化可見紙紋，同時維持文字清晰，避免看起來像布料或石材。


**先確定平滑與法線，再烘焙：**最終烘焙前，逐類表面比較 Shade Auto Smooth／Smooth by Angle、Shade Smooth 與有意使用的平面著色。對使用者的硬表面挖孔／凹槽流程，先在工作用烘焙網格設定依角度平滑與必要的 Sharp 邊，並檢查高模來源及低模目標的法線。連續柔順曲面若比較後更適合普通 Shade Smooth，則採用並記錄理由。不能只依三角面或四邊面來決定平滑／平面著色。Weighted Normal 是可選的法線加權處理，不能取代硬邊與角度平滑的判斷。

切線空間烘焙前，先確定拓撲、UV、Sharp 邊／平滑角度、自訂法線及相關修改器順序。烘焙與交付模型應使用一致的求值法線與三角化方式；隔離或合併的烘焙代理也要保留這些資料。依需求保留可編輯四角網格，同時固定求值時的對角線。烘焙後若更改這些條件，就要重新檢查並重烘受影響貼圖；不能只在烘焙後加 Auto Smooth 就當作修好。先關閉 Normal 貼圖、用中性材質檢查，再於中性光／掠射光及相關 Rig 姿勢檢查烘焙結果。記錄實際角度與比較結果，不規定所有物件都用同一角度，也不宣稱平滑法線能修復爛佈線或錯誤投射。Blender 4.4 實作背景：[Smooth By Angle](https://docs.blender.org/manual/en/4.4/modeling/modifiers/normals/smooth_by_angle.html)。

**不只檢查原物件，也要檢查烘焙代理：**複製未經求值的網格可能漏掉修改器產生的法線；合併或移開小零件也可能改變自動法線與數值精度。使用預定的最終求值狀態，代理整理完成後，比對對應三角形頂點、UV 與分離／自訂法線，並記錄符合資產尺度的容差。必要時保留或還原法線，不能假設 Join 成功就代表明暗基準一致。高模重新平滑時，要檢查原有切線法線輸入，決定保留、重投射、替換或獨立恢復細節；避免重複編碼明暗，也不能默默丟失微細節。對應零件烘焙前，讀取[烘焙代理檢查](references/production-checklist.md#bake-proxy-consistency)。角度平滑可存成 Blender 原生 Sharp 邊／法線資料或適用的修改器，須說明使用方式；3D06 的角度、容差和格線尺寸只是此案例的實測值。

**可重用的程序來源與圖集流程：**使用程序材質製作烘焙交付物時，保留可編輯來源與另存的圖集版本，說明兩者用途及重新烘焙關係，區分同一網格的材質烘焙與真正高模投射至低模。依 [material-authoring-and-bake-workflow.md](references/material-authoring-and-bake-workflow.md) 執行 3D07 驗證過的流程：依實際材質尺度調整、檢查單一 UV tile、比較來源與烘焙近照、檢查貼圖路徑與重開檔案。階段驗收不代表尚未製作的低模已合格。

### R03 — 三角／四角拓撲與乾淨 UV

每個交付的模型網格只能包含三角形與四邊形，禁止 n-gon。每個模型網格都要有有效、實際展開的 UV；隱藏或被遮蔽的已製作零件也包含在內。**NPR 與 PBR 兩種模式都適用**，即使目前只用頂點色上色也一樣：有 UV，之後才能加花紋、貼花、光照烘焙與引擎的光照貼圖。相機、燈光、骨架與無表面的控制器不屬於模型表面。

同時檢查可編輯基礎網格與最後求值的幾何；不能僅加 Triangulate 在最後遮住原始 n-gon，也不能把不合規零件隱藏來通過。曲線、文字、Geometry Nodes 等可輔助製作，但其交付表面必須有合規的可編輯 mesh 和 UV。要另外保留可生成來源時，於製作前約定來源檔與交付模型的分工。

沒有 n-gon 不等於好拓撲：依形狀、細分與變形需求安排邊流，避免長瘦三角、任意扇形切割、意外破洞或重疊面。不要為了統一規則將合理的薄片全部封成實心。

**板面與封口的均衡佈線：**需求偏好四邊形時，依形狀優先採用分布合理的四角區塊／條帶、網格填補或局部對角線。不要預設把圓角板面、螢幕、膠囊面或圓形封口的每個邊界頂點都連到同一個邊界點；表面是平的，也不能自動豁免可編輯的邊流品質。必要三角面應局部化、比例合理，避免橫跨整片表面。圓形封口的網格與極點位置須看明暗及可編輯性，不只看四邊形百分比。均勻指符合曲率與變形需求的分布，不要求每個平面都細分成相同密度。維持已確認的求值三角形預算：兩個三角面合成一個四邊形可改善編輯，但渲染仍需兩個三角形；不能未確認就提高預算，或把混合拓撲改成強制全四邊形。


**挖孔與凹槽：**切割前先規劃孔口外圈與周圍曲面的連接。需要真實孔洞時，優先使用局部環狀／O-grid 或等效的受控三角／四角區塊，讓倒角與壁厚之間的環線一致，並銜接外殼網格。避免把孔口用長瘦三角扇形連到遠處角點或無關孔洞。Boolean 可輔助製作，但要整理結果；自動三角化、零 n-gon 或平滑法線本身都不能證明佈線合格。段數依可見曲率與明暗需求配置，不照搬其他資產的固定數字。檢查可編輯線框、中性光與掠射光近照，在相關姿勢確認沒有夾痕、波浪、不均勻倒角、輪廓破壞與變形問題。驗證項目見 [production-checklist.md](references/production-checklist.md) 的挖孔檢查。

製作有限面數的版本時，依輪廓、深度／視差、變形及互動需求分類孔洞。使用者同意後，小型固定凹孔可用連續低模表面上的暗色、切線法線及粗糙度烘焙表現；這不會產生真正的洞或正確近距離視差。不能只為省面就壓平可動按鍵、必要間隙或影響輪廓的孔洞。烘焙時隔離對應零件，避免相鄰可動件投射到錯誤表面；檢查通道對齊、預定觀看距離及動作極限。3D06 允許省略挖孔幾何是此資產的授權，不是所有產品的通則。


「乾淨 UV」須檢查重疊、退化、拉伸、接縫、padding、texel density 和貼圖覆蓋。預設非重疊；鏡像、重複堆疊或平鋪需先說明並取得該資產的同意。使用者要求 UDIM 時，先確認 tile 規劃與接收端支援，再交付對應 UV 及各通道貼圖，不能只有多格 UV。

根據輪廓、曲率、貼合與變形需求分配面數。近乎平貼的貼紙／標籤使用足以保留外形和貼合的精簡三角／四角網格，不預設沿用高密度瓶身網格。減面後檢查弧形邊緣、穿插與已確認的貼圖／UV 對齊。

### R04 — 製作前確認參考、未知與遮蔽結構

**第一次執行前完整複述需求。** 只有在**每個新資產第一次製作**時（包括新網格階段——例如新的進化形態——第一次建置，或第一次做 Rig）才需要完整的整合摘要。之後依使用者回饋做的調整——造型、比例、配件、顏色、小幅拓撲或材質變動——**不需要**再做完整摘要：用一兩句話說明要改什麼，直接改並回報。只有當調整會改變已確認的預算、風格模式、交付物或目標引擎，或會捨棄已確認的成果時，才先詢問。第一次執行時，在修改製作資產前，先用使用者的語言清楚整合說明：預期成品、需保留的來源與版本、外觀與幾何變動、包含／省略部件、面數計算方式與預算、UV 圖集數及解析度、材質通道與烘焙方法、保留／更改的 Rig 行為、交付物與重要品質取捨。區分使用者明確要求、沿用的已確認規格、助手提案，請使用者核對整份摘要並釐清剩餘的重要未知。即使大部分細節已知，仍需完整複述；取得該範圍確認後直接執行，不重複詢問同一要求。只有新出現的重要變更才暫停受影響部分。確認前可繼續文件與參考分析。

建模前先根據實際看過的參考填寫 [production-brief.template.md](assets/production-brief.template.md)，用圖示標記或文字列出：可確認資訊、推測、未知尺寸／比例、參考衝突、不可見部位與可選內構。

把影響造型、結構、材質或工作量的未知項目集中詢問使用者，例如鍵帽頂面長寬、鍵帽底部、軸體、外殼厚度或接頭內部。對遮蔽部位提供「完整製作／簡化／不製作」等可理解選擇，說明用途與影響，並問是否還有遺漏結構。**在製作細節得到確認前，不開始生成模型。**可以繼續蒐集參考、測量已知資料與準備文件。

使用者已確認的規格或明確授權估計的範圍直接沿用並記錄，不重複索取同一許可。遇到新的未知時，先問再做受影響部分；可繼續不受影響且已確認的部分。沒有回覆不代表同意，不能把投影比例或商品尺寸冒充實測尺寸。

每個新資產建模前先問目標面數，或 **低模／中模／高模** 等級。依資產複雜度、用途及鏡頭距離判斷等級，提出具體基礎／求值預算，清楚區分面數和三角形數，並記錄使用者確認或明確委託判斷；不訂全資產共用的等級門檻。同時詢問 UV 要拆成幾張**方形貼圖圖集**、各張解析度（例如 1024 × 1024 或 4096 × 4096）及 UDIM 需求。張數指 UV 圖集，不是 PBR 通道檔案數；以方形優先。沿用已確認答案，已接受資產的非方形 UV 或較高面數，未被要求時不擅自重做。

## R08 — 補充產品參考搜尋

使用者提供產品照片時，若有助於釐清型號、比例、材質或內部結構，可以主動上網搜尋補充產品圖片及規格，無須為搜尋本身另問許可。優先採用同型號的官方資料；需要其他角度時，可參考可靠零售商或評測。

記錄網址、查閱日期、型號／版本、實際看過的圖片或規格，以及資料能證明的內容。檢查鍵位配置、世代、材質款式、地區與版本差異，不把相似款默認為同一款。區分宣傳圖片、標示尺寸及推測；只找到網頁但未檢視內容，不算畫面證據。

把影響製作的補充發現與使用者原始參考一起放入 R04 確認表，請使用者確認是否適用；有矛盾時明說，不能默默取代原始參考。搜尋已獲允許，但採用不確定尺寸或新增內構仍遵循 R04。來源無法存取或無法確定時，說明缺口並提問。網路上的產品圖片不因此自動成為可交付的授權貼圖。

## R06 — 交付保持 Selection 與 Extras 開啟

交付檔案中的所有物件及 Collections 都要保持可選取，不能留下 `hide_select` 鎖定，包括上層 Collection 造成的限制。每個保存的 3D View 都要開啟 overlays 與 `show_extras`，讓使用者能在預定視圖找到燈光、相機等內容。重開交付檔案後，檢查設定並實際嘗試選取。

不能交付只有控制器能選的預設狀態，不能要求使用者執行解鎖腳本，也不能為美觀而全域隱藏 Extras。之後若使用者明確要求獨立的動畫專用模式，切換應可逆；交付前仍需恢復 Selection 與 Extras 開啟。這項要求取代先前「有編輯模式切換即可」的建議。

## R09 — 按物件類別整理貼圖資料夾

外部貼圖按有意義的物件類別分資料夾，同類別完整通道放在一起，例如 `textures/glass/`、`textures/cap/`、`textures/labels/front/` 與 `textures/labels/back/`。類別內有多個材質組時可再用清楚命名的子資料夾。共用貼圖只放在一個明確的共用／類別資料夾，記錄使用它的物件，不重複複製。同步更新 Blender 圖片路徑及 manifest，重整後檢查外部檔、打包貼圖、相對路徑及重新開檔。打包不能取代使用者要求的 Windows 資料夾整理。

## R10 — Armature 控制器與 Rig 需求核對

依 blendsmith 的 Blender 工作規範，要求 Ctrl／控制器時，必須使用 **Armature，讓動畫師在 Pose Mode 操作控制骨並設定關鍵影格**。Object Mode 的 Empty 或獨立 Curve 控制器不符合此要求。可用 Custom Shape 顯示控制骨外觀，但動畫師操作的對象仍是 Pose Bone，不是外觀物件。這是本專案規範，不宣稱所有 Blender Rig 都只能這樣製作。

建立或大幅修改 Rig 前，先問清楚使用者要做哪些動作、控制到什麼程度。詳細描述並總結階層、附屬零件、變換空間與軸向、輸入與連動關係、限制、縮放規則、脫離／重新接合及關鍵影格工作方式；區分已確認要求與助手提案，再請使用者核對摘要，確認後才實作相關控制。沿用已回答的需求，確認後不重複要求同一許可。使用製作簡報的 Rig 欄位，單一資產機構留在該資產規格內。

實際驗證 Pose Mode 的一般變換工具與關鍵影格、允許／禁止通道、父層帶動、附屬細節、狀態邊界、反向操作、重開、播放與時間軸跳轉。變換通道鎖定不等於禁止選取：限制動作時仍遵守 R06 的 Selection 與 Extras。可用輔助骨、Constraint 與 Driver 支援機構，但動畫師操作入口必須清楚；只有 Driver 數學測試通過不代表動畫操作合用。

## R11 — 交付實際的 Blender 檔案

約定交付 Blender 資產時，助手必須自行執行已授權的生成流程，並在約定交付資料夾保存版本化 `.blend`。生成腳本（`.py`、`.ps1`）、指令、預覽及操作說明屬於附加來源，不能取代使用者要求的模型。除非使用者明確要求只交付腳本，不能把取得第一份可用 `.blend` 的 PowerShell／Python 執行步驟留給使用者。

**程序化來源專案：**若專案設定檔註明使用者正在學習程式化建模（如本 repo），則**兩者都要交付**：生成腳本（作為可編輯來源 commit，寫得易讀、有註解，方便學習），**以及**執行腳本後產出、已驗證的版本化 `.blend`。沒有這種設定檔時，腳本可有可無，可驗證的 `.blend` 才是交付物。

製作初期確認現有工具能操作 Blender，且能寫入輸出位置。如果無法執行或執行失敗，明確說明阻礙及模型尚未生成；提供的腳本要標示為未執行／部分成果。不能把只有腳本的套件說成完成的資產，也不能默默安裝超出授權範圍的軟體。

宣稱交付完成前，等待生成與存檔結束，確認指定檔案確實存在且大小非零，再以新的 Blender 程序重新開啟該存檔。依[交付檢查表](references/production-checklist.md#7-save-reopen-and-deliver)檢查預期場景及必要依賴。失敗流程留下的舊檔、腳本成功退出或檔案大小本身，都不能證明本次交付有效。記錄實際檔名／版本、大小、存檔及重開結果；必要檢查未解決時仍屬未完成。

提供使用者可存取輸出資料夾內實際 `.blend` 的可點擊連結，或透過使用環境支援的下載機制附上檔案。確認提供的成果就是已檢查的檔案。只存在於使用者無法存取的助手環境中的路徑，不算交付完成。有存取／附件限制就明說，不能未經確認就宣稱檔案已出現在 Files 面板。每個約定交付資產的製作節點都適用；純分析、純檢視或明確只要腳本的任務不要求新增模型檔。

## R12 — 遊戲引擎交接（Unity／Unreal）

資產要給遊戲引擎使用時，匯出檔也是交付物的一部分。

- 在製作簡報或專案設定檔記錄目標引擎與版本。用該引擎的預設設定匯出（座標軸、單位比例、平滑、頂點色、匯出哪些物件），並把設定寫在腳本或設定檔裡，不只靠記憶。
- 匯入後比例為 1、前方／上方軸向正確：資產站在原點上、面向引擎的正前方，根物件不需要額外旋轉。匯出前在 Blender 套用旋轉與縮放；物件原點保留在動畫需要的位置。
- 平滑資訊以面平滑（或法線加 Sharp 邊）匯出，避免引擎回報缺少平滑資訊。頂點色遮罩用引擎 shader 預期的色彩空間匯出，並記錄。
- 使用靜態光照時，Unreal 需要第二組不重疊的 UV 作為光照貼圖；Unity 可在匯入時自動產生。記錄光照貼圖 UV 是自備還是自動產生。
- 能使用引擎時，把實際匯出檔匯入引擎，記錄朝向、比例、材質／頂點色、三角形數與描邊／shader 結果。無法使用引擎時，匯入測試標記為 **NOT RUN**；只在 Blender 檢查不能證明引擎相容。

## 製作與驗收流程

1. **確認規格**：確認用途、鏡頭距離、尺寸、內構、材質／貼圖、UV／UDIM、rig、預算及交付格式。未確定的產業參數不得自行寫成硬標準。
2. **主要造型**：先比對輪廓、比例、主要接合與多視角灰模，再細化。是否需要使用者檢查灰模、材質樣片或 rig，記入已確認的製作節點，不任意增加重複審批。
3. **可編輯構造**：按實際功能拆件，安排原點、命名、Collection、材質與修改器。重複構件依用途使用實例；細小紋理按鏡頭需求分配給貼圖或幾何。不得以超高面數代替合理建模。
4. **拓撲、UV、材質與控制**：依 R01–R03 實作，Rig 同時遵循 R10。套用變換或修改器前評估對尺寸、UV、法線、parent 和 rig 的影響。rig 任務要讓活動件、字符、裝飾與附屬細節一起運動。
5. **實際檢查**：執行 [production-checklist.md](references/production-checklist.md) 的適用項目，記錄 PASS／FAIL／NOT RUN／N/A 及證據，包含 R06 的交付檢查。未跑的項目不可寫成通過；不得靠單張美圖、封閉網格或面數宣稱可投入製作。
6. **交付與記錄**：遵循 R11 與 R12，交付可打開的版本化 `.blend`、引擎匯出檔、所用貼圖與必要依賴、簡短操作說明、測試結果及已知限制。先寫 worklog，再提供使用者檢查入口。

## 透過實測修訂 skill

使用者提供新模型後，先依 R04 做製作簡報；不因建立了 skill 就自行選模型開工。每輪記錄「要求 → 行為 → 測試／觀察 → 決策依據摘要 → 交付 → 使用者回饋」。決策摘要說明可核對的理由與取捨，不記錄內部逐步思考。

收到回饋時，保留原文或明確標註的摘要、來源與日期，連結到該版本的工作。在原 worklog 追加有日期的回饋節，或另建回饋 worklog 並互相引用，不能改寫先前歷史讓它看似一開始就通過。使用者授權翻譯歷史文件時，可以改變語言，但必須保留歷史事實並註明這是翻譯。

可重現的流程缺陷與使用者明確的新要求，更新到適用的規則；單一資產偏好保持局部，助手補充提案標為待確認。修改規範時增加版本、說明差異與相容影響，同步繁體中文副本，並執行格式／連結檢查。尚未模型實測的規則保持標記；下一次相關實測驗證修訂有沒有減少返工。
